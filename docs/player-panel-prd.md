## 1. 产品目标与术语

玩家在查看和更换装备时，能够在独立小窗口中观察完整角色及其展示动作，同时保留窗口之外的游戏世界画面。体验参考《博德之门 3》的角色面板，不假定或复制该游戏的内部实现。

当前最重要的交付是可在游戏内使用的单角色摄影棚渲染逻辑，沿用第 2 节确定的渲染顺序。在此基础上，后续扩展为保留 Skyrim 分类的网格背包、环绕角色的装备槽，以及支持随从库存切换的交易和物品交换界面。

| 术语 | 定义 |
| --- | --- |
| O | 当前展示对象对应的世界角色，继续由原游戏逻辑管理。当前阶段为实际玩家；后续角色切换阶段可为选中的随从。 |
| P | 面板内的独立展示角色，其外观来源于 O，其动作与展示状态独立。 |
| 摄影棚 | 仅包含 P、必要装备与展示背景的独立渲染场景，具有自己的相机、灯光和深度。 |
| 面板 | 摄影棚输出在游戏画面中占据的不透明矩形区域，不是额外的操作系统窗口。 |
| 共存 | 同一帧同时显示世界画面和角色面板；不要求两个场景在 GPU 上并行执行，也不要求菜单期间世界模拟继续运行。 |
| 当前角色 | 背包／装备面板当前选中的玩家或随从；切换该对象表示切换库存与展示对象，不默认包含切换世界中的操控角色。 |
| 交互对象 | 当前交易或交换的另一方，例如商人、随从、容器或可搜刮尸体；与当前角色分别记录。 |

核心要求：

1. **外观一致**：P 显示 O 当前的脸部、身体、服装、护甲和实际装备／持有的武器；不带入战斗血渍等无关临时污染。
2. **动作独立**：P 的姿态、动画进度、朝向和武器展示状态不必与 O 一致，面板操作不改变 O 的动作。
3. **渲染逻辑复用**：摄影棚尽量使用世界角色相同的材质与着色逻辑，使玩家安装的相关渲染修改能够作用于 P；摄影棚的相机、照明和背景独立。
4. **物理与换装**：在声明支持的版本与配置中，P 能应用 CBPC 和 SMP 效果并持续同步换装；静态快照或自制弹簧摆动不能替代这些要求。

“一致”不要求不同照明、视角和姿态下像素相同。“任意模组自动生效”是兼容方向，不是已有技术保证；实际支持范围必须有版本与效果级验证记录，不得以局部出图宣称全面兼容。

## 2. 确定的画面合成顺序

| 阶段 | 行为 | 输出与边界 |
| --- | --- | --- |
| 1. 世界画面 | 正常绘制游戏世界，完成该世界视图的游戏内后处理。 | 保留 O 与原场景，不移动主相机为 P 取景。 |
| 2. 角色面板 | 在独立摄影棚中绘制 P，完成必要的局部处理，再把结果作为不透明矩形合成到世界画面上。 | 仅覆盖面板区域，不与世界共用深度。 |
| 3. 其他 UI | 绘制背包内容、面板控件、提示框、光标及其他需要覆盖面板的游戏 UI。 | 保持正常交互与遮挡层级。 |
| 4. 最终后处理 | 在已合成的画面上执行 ReShade 等外部最终画面效果。 | 按此顺序，世界、面板及已绘制的 UI 均可能受影响。未安装时直接显示。 |

```text
世界 O → 世界渲染 → 世界视图后处理 ──────────────┐
                                                ↓
摄影棚 P → 独立渲染 → 必要局部处理 → 不透明矩形合成
                                                ↓
                                      其他 UI → 最终后处理 → 显示
```

这是产品要求的可见合成顺序。离屏准备工作可以在安全时点调度，但不得因此使用过期角色数据、破坏 UI 层级，或使摄影棚状态泄漏到世界绘制。

### 2.1 摄影棚的独立边界

- 使用独立相机、灯光、背景、颜色目标和深度目标；需要时提供自己的材质缓冲与历史状态。
- 摄影棚内部正确处理身体、装备的遮挡和透明材质。不透明窗口不等于关闭头发、薄纱和粒子的透明处理。
- 最终合成不提取角色透明轮廓，不计算 P 与世界物体之间的遮挡，不把 P 的深度写入世界深度。
- 世界天气、雾、附近物体和 O 的地理位置不决定摄影棚的构图与展示灯光。
- 窗口外的世界画面、主相机和下一帧渲染不得因摄影棚绘制产生异常。

### 2.2 后处理边界

- 世界视图的景深、受击模糊等不自动继承到摄影棚；摄影棚不重复执行完整世界后处理。
- 皮肤散射、材质合成等即使通过全屏 Pass 实现，仍可能是 P 正确着色的必要环节；不能仅因其“全屏”而省略。
- 摄影棚输出必须与合成目标的颜色表示一致。若输出为 HDR、目标已完成色调映射，应先完成匹配转换，避免发灰、过曝或重复色调映射。
- 最终调色、颗粒等读取颜色的效果可共同处理合成结果。依赖深度、法线、运动矢量或历史帧的外部效果，不会因颜色合成而自动理解摄影棚。
- 首版按普通 UI 面板定义外部深度效果的边界，不承诺向 ReShade 提供统一的双视图深度。由此产生的不兼容须在支持矩阵中明确，不得宣称该效果已完整支持。
- 游戏内后处理、第三方渲染框架与最终后处理按实际接入阶段分类，不按插件名称推断执行顺序。

## 3. 用户流程与交互

1. 在有效游戏会话中打开面板；原型使用热键入口，产品集成面向背包界面。
2. 准备 P 的外观和摄影棚资源，期间显示准备状态；窗口外保留世界画面。
3. P 以独立待机姿态显示。玩家可查看角色，并使用面板控件旋转展示方向或切换展示动作。
4. 背包装备操作仍由游戏处理。装备最终生效后，面板同步显示结果。
5. 关闭面板后恢复正常输入状态，停止不必要的摄影棚绘制和展示更新。

面板应适配背包留出的展示区域，并让文字、确认弹窗和光标显示在其上方。后续背包采用分类网格展示，并围绕角色安排装备槽，详见第 9 节。具体尺寸、按键、原物品 3D 预览的安排及与现有 UI 模组的配合方式仍需确定；参考 Grid Inventory 不等于确定将其作为依赖。

## 4. 功能需求

### FR-01 外观与装备同步

- 打开时读取 O 当前生效的第三人称外观和装备；O 处于第一人称或未出现在主相机中，不应阻止完整展示。
- 同步范围包含脸部、肤色、体型、头发、持久外观覆盖、护甲和左右手装备；按支持清单覆盖种族、骨架与外观模组。
- P 的武器属于同一装备结果，但收放位置和姿态可按展示动作决定，不要求复制 O 的瞬时武器姿态。
- 以装备实际生效结果为准，不把鼠标高亮或尚未完成的装备请求当作最终外观。
- 连续换装时合并刷新，较早完成的加载结果不得覆盖较新的状态。允许暂时保留最后一个有效画面并提示更新。
- O 的 3D 重建后，P 应重新取得有效外观来源；不得跨读档持有失效节点作为有效数据。
- 不修改 O 的库存、装备或与其他角色共享的基础记录来完成预览。

### FR-02 临时污染过滤

- P 不同步 O 因战斗产生的血渍等已识别的临时 decal／污染效果。
- O 的原有血渍不因清理 P 而被删除。
- 妆容、纹身、角色设计中的疤痕等持久外观应保留，不能通过删除所有 Overlay 或相关材质来清理血渍。
- 对直接写入纹理、无法区分来源的第三方污染，不宣称已可通用剥离；须记录适配需求与实际限制。

### FR-03 独立动作与物理

- P 独立维护姿态、动画进度与根变换，至少支持稳定待机和一种可切换展示动作。
- 动作资源需支持目标运行时与骨架兼容的 `.hkx`；实际可播放与可切换才计为通过，骨骼探针只验证驱动链的前置条件。
- O 攻击、蹲伏、游泳或转身时，不自动把相同姿态强加给 P。
- P 的动作切换、根运动及武器展示不改变 O，也不在世界中触发攻击、施法、碰撞或交互。
- 武器与装备附着于 P 的骨骼；动画切换和换装后不得残留错误附着。
- 在明确版本、身体／骨架和配置分工下支持 CBPC 与 SMP，其模拟状态和更新时间独立于 O。分别验证两套物理，不要求同一骨骼同时由两个解算器写入。
- 独立程序化摆动不是 CBPC／SMP 兼容实现；如需降低该要求，必须另行取得用户同意，不能用“满足独立物理的精神”代替验收。

### FR-04 摄影棚渲染

- 按第 2 节顺序在世界画面上合成不透明面板，从首个原型开始保留两个视图。
- 使用可控的相机和灯光，默认保证完整角色及常见装备可见；首次不提供完整摄影棚编辑器。
- 尽量复用引擎角色装配、材质和绘制能力。通用材质替换、动态材质和角色专属效果分别验证。
- 必须正确处理所声明支持的蒙皮、透明裁剪、透明混合，以及必要的阴影／材质合成过程。
- 摄影棚使用自己的视图数据。不得依赖 O 在主画面可见、世界当前帧恰好绘制到某个角色 Pass 才能生成 P。
- 不得通过移动 O、切换主相机或覆盖整个世界画面实现面板。

### FR-05 暂停、UI 与输入

- 支持世界正常运行时的双视图验证，以及背包暂停世界时的 P 动画与必要换装刷新。
- 暂停时不通过额外推进世界模拟或 O 的动画来驱动 P。
- 在没有装备操作的观察窗口内，O 与附近 NPC 的动画、物理状态不得因 P 的更新而额外推进；正常的背包装备装配更新另行记录，不能与模拟推进混为一谈。
- 只消费面板操作所需输入；关闭或失去焦点后不残留拖拽、按键、鼠标捕获状态。
- 原游戏装备操作、退出操作、确认弹窗和光标保持正常。

### FR-06 生命周期与失败处理

- 没有有效游戏会话、正在读档或返回主菜单时，不新建可用预览。
- 重复开关、换装、切场景、读档及渲染目标重建时，取消失效请求并安全重建所需资源。
- 安全释放必须有实际析构与内存／显存回收证据。停放不释放仅是诊断阶段的临时绕过，不计为生命周期通过；记账条目上限不等于实际分配上限。
- P 不成为可攻击、可搜刮或可交互的世界 NPC，不留下存档残留或可观察的游戏逻辑副作用。
- 预览失败时显示不可用状态并允许关闭；原游戏与背包仍可使用。
- 不静默退回显示 O、替换主世界画面或复制 O 的姿态，并将其算作需求完成。

## 5. 兼容性、范围与性能

### 5.1 兼容性验收原则

复用相同引擎接口不等于兼容所有插件。只针对 O 的身份判断、绑定固定渲染目标的效果、第三方内部状态，以及不同 Hook 链都可能需要适配。

| 类别 | 验证内容 |
| --- | --- |
| 游戏运行时 | 锁定 EXE、SKSE、Address Library 和 CommonLibSSE-NG 版本，分别记录结果。 |
| 原生渲染 | 完成材质、蒙皮、透明、摄影棚照明和合成基线。 |
| Community Shaders 等框架 | 按版本与功能记录 P 的材质、光照、局部处理是否正确；不能由原生基线外推。 |
| ENB 等其他路径 | 单独调查其接口和阶段，未验证前不宣称兼容。 |
| ReShade | 核实合成位于效果执行之前；区分颜色效果与依赖深度的效果。 |
| 外观／动画／物理模组 | 分别验证形变、覆盖纹理、附加节点、独立动画和物理更新。 |

支持矩阵至少记录：版本组合、测试角色／装备、效果开关、结果、已知限制和验证证据。候选基线为本地前期记录中的 Skyrim 1.6.1170 与 SKSE 2.2.6，实施前重新核实；不将其当作本次已验证状态。

### 5.2 当前渲染阶段边界

- 先针对单一非 VR 运行时和普通人形玩家形成可验证基线；新增运行时、变身或特殊骨架须另行验证。
- 独立 Actor 与直接复制场景图均为候选承载方式。以动作、CBPC／SMP、持续换装、世界隔离和安全回收的证据决定路线，不因静态显示成功锁定架构，也不因无效探针排除路线。
- 当前渲染与基础集成阶段不实现分类网格背包、完整装备槽界面、随从面板、跨角色交易等第 9 节扩展需求；这些是后续产品目标，不再列为整个项目的非目标。
- 当前仍未要求试穿、幻化、外观编辑、摄影导出或通用双视图后处理框架。渲染 P 不要求复制一份完整游戏库存。
- 后续支持角色切换不自动包含多个 P 同屏绘制；当前继续以一次展示一个角色为实现边界。
- 未支持的变身或角色形态显示明确状态，不用默认人形冒充当前角色。

### 5.3 性能与稳定性

- 关闭面板后停止摄影棚绘制与不必要的展示更新，不进行持续 GPU 读回。
- 面板开启时按窗口需要选择输出尺寸，不默认再渲染一份全屏世界。
- 验证时记录开启前后的 CPU／GPU 帧耗时、显存占用，以及打开和换装延迟；反复开关后不持续累积资源。
- 首个双视图原型测量基线后，在功能扩展前确定量化预算。未测量前不填写虚构的帧率或毫秒承诺。

## 6. 当前渲染与基础集成的验证阶段

以下 M0–M3 保持原有渲染与基础集成范围。M2 的背包集成不等于第 9 节的完整背包改版；后续扩展另行拆分工作包，不以增加本轮 UI 工作替代 M0 渲染验证。

| 阶段 | 交付与通过条件 |
| --- | --- |
| M0：双视图渲染验证 | 从开始就同时显示世界与摄影棚；在其他 UI 之前合成不透明窗口；验证 P 着色及世界下一帧不被污染。可先固定姿态，但必须使用独立展示实例。 |
| M1：外观与动作闭环 | 同步支持范围内的外观和装备，过滤临时血渍；P 独立播放与切换展示动作，O 不受影响。 |
| M2：暂停与背包集成 | 暂停时 P 可更新，背包换装正确同步，输入与 UI 层级正确，关闭及读档清理完整。 |
| M3：目标环境兼容与性能 | 在明确版本组合上验证渲染框架、最终后处理及外观扩展，提交支持矩阵和性能结果。高风险兼容性可在 M0 提前验证。 |

### 6.1 范围修正：面板仅在菜单界面显示（2026-10-01，用户决定）

- 原 A01（世界画面中开面板并移动主相机）及其世界对照类场景整体推迟，由"菜单内验收清单"替代（见 m0-handoff.md 的阶段 1）。

- §2 的帧内合成顺序（面板在其他 UI 之下、最终后处理收尾）在菜单帧内继续有效。
- 当前实现天然符合该范围：重放与合成只在有菜单光照 pass 的帧发生，无需删改代码。

### 6.3 摆姿探针验收协议与已取得的证据

详细执行与回传格式见 [2026-10-09 测试单与后续记录](scene-graph-copy-next-test-2026-10-09.md)。后续 S2P1–P4 已修正顺序并取得摆姿与画面随动证据；本节保留基础验收协议，不要求重复全部旧实验。当前 HKX 工作包以 §6.4 为准，GPU 内部绑定／消费细节仍不能由 CPU 转储直接证明。

**准备条件**：固定源码提交、DLL／PDB SHA-256、实际 CommonLib checkout、游戏／SKSE、渲染与身体／骨架版本；选择一个确实出现在画面的身体或护甲 draw，确认目标骨骼在其有效权重／palette 中。测量修正后至少有一轮 CBBE 与一轮 UBE，先分别建立静态基线。

**必须固定的执行顺序**：摄影棚基础摆位完成 → 施加受控骨骼变换 → 引擎 pass 准备与必要蒙皮更新 → 实际 draw → 合成。不允许中间再从捕获快照覆盖变换。

| 测量点 | 要记录什么 | 作用 |
| --- | --- | --- |
| T0 基础摆位后 | capture／帧号、目标几何／骨架根／骨骼身份、基准世界矩阵和实际绘制目标 | 建立同一个副本、同一个可见 draw 的基线 |
| T1 施加探针后 | 同一骨骼的姿态、有效见证点／方向、受控增量、CPU 数组地址与原始内容 | 证明变化确实施加到目标；保留写入前的数据，避免循环分类 |
| T2 实际 pass 提交前 | 相同节点与 CPU 数据、frameID／矩阵数、实际 pass geometry | 检查基础摆位或引擎准备是否覆盖修改 |
| T3 实际 draw 后 | 节点／CPU 数据是否被重建；GPU 实际绑定的骨骼缓冲、偏移／范围和内容；画面 | 连接 CPU 写入、上传与着色器读取，定位断点 |

先做“探针关／开”的配对测试，只改变一项；保持相机、装备、根方向、光照与目标 draw 一致。先仅改变节点、不手写矩阵；仅在数据语义与上传位置有证据后，才进行可恢复、有限值的缓存干预。不得用矩阵名或一次抓帧推断消费关系。

判定要求：

1. T1 未变化或见证点无有效判别力：实验无效，修正探针，不判路线失败。
2. T1 变化、T2 恢复：执行顺序／覆盖问题，修正更新链，不宣称 GPU 不使用数据。
3. T2 保持变化、GPU 数据未变化：上传／缓存／帧号路径未建立；继续定位，不直接判所有骨骼驱动不可行。
4. GPU 正确反映变化、画面不变：核对真实 draw、palette／非零权重、矩阵空间与采样范围，仍不能只凭数组写入判定机制。
5. 画面跟随且 O／NPC 无额外变化：仅通过摆姿前置测试；HKX 播放、两种物理和连续换装必须分别验收。
6. 出现世界异常、越界迹象、崩溃或无法确认构建身份：停止该轮、保留原件，后续项填未测试。

S1 需另行验证析构前置条件、活跃／停放／丢失记账的实际分配数量，以及重复换装、读档和退出后的内存／显存回收。当前已知停放策略不安排长时间压力测试，也不把反复停放记为资源稳定。

S3 必须分别证明 P 的 CBPC／SMP 注册、定向推进和注销。在没有装备操作的观察窗口内，暂停的 O／附近 NPC 保持冻结；解除全局物理暂停不构成通过。自制弹簧摆动不得代替两套指定物理的验收。

下一轮交付至少包含完整日志、匹配 PDB 与 manifest、探针关／开的截图及对应图形抓帧（如进行 GPU 判读），失败需附崩溃日志。日志截图中的片段和“我看到不动”不能替代执行链证据。

当前摆姿前置机制已取得正结果；实际动画数据、持有与独立采样按 §6.4 继续，独立物理实例按 §6.5 验证。安全回收、CBPC／SMP 和持续换装分别验收，不能由摆姿正结果代替。

### 6.4 下一工作包：从真实播放生命周期取得一段可采样 HKX

详细准备与回传见 [HKX 下一工作包测试单](s2-hkx-next-work-package-2026-10-10.md)。本节是规划与验收要求，不表示新的代码、装载接口或采样对象已经实现／取得。

#### 已取得的结果与尚未关闭的问题

- S2P1–P4 的顺序修正、只写副本节点与开／关配对观察支持“节点修改能驱动画面”。继续沿用现有绘制链，不再每轮猜蒙皮槽位或手写不明格式的骨骼缓存。
- HKX1/2 支持骨名映射、直接四元数转换与姿态写入。实测旋转残差 0.03–0.10°、位置残差 0.529–1.614 单位；这是可用的前置机制，尚不是任意动画的精确重放证明。
- HKX11/12 只排除了把所读注册记录直接当动画对象、以及把 0x20 条目的 +0x28 当其资源指针的解释。注册表名字／索引可用，不代表已取得 animation／binding。
- “名字是 MT_Idle、索引对得上”不足以认定它是当前正在执行的实例。某批字段为空不能连带判定引擎标准 binding/control 层普遍无效，也不能否定所有经引擎装载 HKX 的路径。
- OAR 源码的真实播放／混合路径会经 `animationControl->binding->animation` 调用采样；这提供生命周期调查线索，不证明本项目已找到同一有效对象。仅参考源码，不引入 OAR 运行时交互或新依赖。

#### 首选实施顺序

1. **先做有界静态核对**：固定所参考的 OAR commit、游戏／SKSE／CommonLib 与目标运行时；核对真实 Activate／Load／Update／采样调用的对象类型、签名、字段及执行时点。无法解释来源与持有关系时不增加上机盲探轮次。
2. **只读观察一段正在播放的 Idle**：在 O 的正常世界更新中被动观察真实实例，记录 actor、第三人称 graph、clip／context 身份、阶段、实际动画／替换文件身份及索引。不得额外驱动 O、伪造激活或恢复世界模拟来取得数据。
3. **取得可持有的资源与映射**：确认采样对象的真实类型和资源所有者；验证 animation／binding、duration、轨道与骨架。地址可读、数值看似合理和“裸动画校验通过”不是来源证明；不得用轨道 i=骨骼 i 代替映射。
4. **先做确定性采样**：选择这一段已确认动画，用引擎已验证的采样入口在相同 t 重复取样，再在至少三个不同相位取样，验证有限值、输出数量、边界和内容变化。只进行只读采样，不修改原 clip 的时间／状态。
5. **再驱动一份 P**：用已验证的骨名桥接和基准姿态处理实际轨道；仅写 P，在摄影棚时钟上测试暂停、继续、变速和循环。每帧采样更新同一副本，不每帧重新复制场景图。
6. **单独验证续接与回收边界**：展示关闭停止不必要更新；源 3D 重建、资源卸载、读档／新游戏时取消失效引用。S1 未闭环前限于少量单副本短会话，不通过累积停放来掩盖资源风险。

资源持有必须覆盖动画的压缩数据、绑定与轨道表依赖的底层资源。仅保留裸指针，或仅给一个对象加引用但无法保证其包文件／加载器内存存活，不能计为安全持有。若持有机制未知，先完成资源调查，不把 borrowed 指针长期放入播放状态。

#### 映射、真值与误差要求

- animation skeleton、`boneNodes`、`poseLocal`、animation tracks 和 NIF 节点是不同的表。分别记录映射身份与索引，不因为数量相同就按下标连接。
- 缺失骨按所选动作／装备需要判断；Shield／Weapon／Quiver／Belly 和辅助骨不能永久视为无关。重复骨名需以骨架根、父链与所属分支消歧。
- 动画骨架父骨是 NIF 节点祖先，不代表它就是直接父节点。写 local 时需核对中间 CME/helper 变换、基准姿态及坐标空间，不直接套用“祖先匹配→局部坐标相同”。
- 单独调查现有位置残差：比较保留节点缩放与采样缩放、uniform／nonuniform 转换、helper 变换、根位移处理和未解析骨。先固定假设与阈值，再比较，不能只因“排名最好”宣布完全正确。
- 用同动画、同时间、同映射的独立参考做 A/B。O 的最终姿态可能含混合、IK、additive 或物理修正；单个 clip 的采样不能无条件要求等于完整最终 `poseLocal`。标出剔除项或使用可确认的单 clip 参考。
- 至少验证多个非等价相位；重复采样一致只是确定性，不代表能播放。旋转、位置和缩放分别报告误差、参与／跳过的骨与原因。
- 根运动由摄影棚规则接管，不移动 O；未动画化的节点保持明确的基准／参考姿态，不能无条件写零或身份变换。

| 关卡 | 通过条件 | 未满足时 |
| --- | --- | --- |
| H01 构建／实例身份 | 最终包 DLL／PDB 哈希与日志匹配；实际执行阶段、第三人称实例与动画身份有证据 | 不计为有效采样实验；文件名命中不是活跃实例证明 |

下一实验只回答“能否在一个已知真实实例上取得并持有一段可采样动画”。准备阶段解释不了调用与资源链，就不发新的盲探包；进入运行测试后仍无有效实例／对象且没有新的可验证结构证据，则停止本轮、回报未决点，不自动追加未知指针层。
只有来源／映射／持有明确才继续采样；一次 `found=0` 不构成机制不可能的证明，也不授权改变产品要求。

#### 录制回放备选 D 的边界

`poseLocal` 录制回放可用来验证独立时钟、插值、循环与定量重放，是受限备选，不是任意 HKX 文件播放器。
只在 O 正常未暂停的更新中被动录制，数据深复制为 P 自己持有的轨迹；记录骨表版本、时间、缩放、根变换与来源上下文。
不能在背包暂停期间推进 O 以补录，也不能保留对源姿态缓冲的长期引用。自然观察不到的新动作无法由 D 凭空获得。

录制前需确定覆盖完整周期或可接受的拼接窗口。接缝位置、旋转、缩放和速度连续性，以及重采样／四元数插值分别验收；随意截取几秒不等于无缝待机。
源 3D／骨表变化时重新绑定或中止，不将旧下标应用于另一套身体。D 的重放成功只计为回放前置能力，不能代替真实 HKX、展示动作切换、CBPC／SMP 与持续换装的完整交付。
不承诺“小时级交付”或“机制全部验证”；启动 D 需明确它的受限范围，不因 HKX 取数失败就静默将其算作 FR-03 完成。

#### 优先级与回传

HKX 按本节取得一段真实 clip 并做短会话采样；物理可按 §6.5 先以确定性骨骼输入独立验证，不等待完整 HKX 播放链。两条工作包的正结果不得相互替代。S1 安全回收仍是反复开关、持续换装与长会话测试的前置门槛；自制物理不能替代指定求解器。
保存完整日志、最终包 manifest、匹配 PDB、生命周期阶段／实例与资源链记录、三个相位输出、误差统计与控制条件；需要时附图形抓帧。中间 dirty 构建必须保留完整源码差异和二进制哈希，不能只写“与最终包相同”。

当前交付是上述逻辑与测试规划，等待按此准备的下一轮结果；本次没有修订动画取数代码或生成新 DLL。

### 6.5 可验证方案：复制场景图上的独立 SMP／CBPC 实例

详细上机操作、对照条件、失败定位与回传模板见 [S3 独立物理游戏内测试单](s3-independent-physics-validation-2026-10-10.md)。
本节纳入用户认可的验证方向，**尚未实现，不表示当前 DLL 已具备以下接口或控制项**。
HKX 可加载和独立采样是完整方案的工作前提，其实际取数、持有与映射仍按 §6.4 验收。

#### 目标与独立边界

保留直接复制场景图的 P，为其创建独立动画实例、SMP 实例与 CBPC 实例。P 的时间、运动状态、碰撞集合和写入目标独立于 O。
不将 P 放入 Skyrim Cell／WorldSpace，不为预览移动 O，不通过临时替换 O 的 3D 指针或解除全局暂停接入物理。
求解器使用的独立 Bullet 物理世界是模拟容器，不是游戏世界空间。

场景图复制只提供节点、网格与蒙皮引用，不能据此认定物理系统也被复制。
必须重新创建刚体／约束、节点运动状态、配置绑定与碰撞体；不得共享 O 的可变模拟状态、源节点指针或以玩家 FormID 作为预览状态键。
种族、性别、体重、骨架及装备身份等由只读来源转换为预览属性；涉及战斗、姿态等条件时，明确使用展示状态还是来源快照，不能悄悄持续跟随世界角色。

| 上下文内容 | 要求 |
| --- | --- |
| 副本与代次 | 明确 preview ID、capture ID、骨架／装备 generation；异步结果只能提交到匹配代次 |
| 动画状态 | 自有时钟、clip／轨道映射、基准姿态与根运动规则；不修改源 clip |
| SMP 状态 | 独立模拟容器、系统／刚体／约束／网格碰撞，所有节点绑定属于 P |
| CBPC 状态 | 独立节点状态、碰撞集合、条件／配置缓存与时间步；核对按骨名全局共享的同步表等隐藏状态 |
| 更新和所有权 | 明确各阶段与线程、工作完成屏障、资源引用及解绑顺序；不能让 worker 与绘制同时写同一骨架 |

#### 两套后端的实施调查范围

**SMP／FSMP**：复用现有配置解析、骨架／装备系统创建和求解路径，扩展预览入口，允许指定副本根节点、装备网格、配置和独立容器。
现有公开 `PluginAPI.h` 提供模拟前后监听，不能直接完成这一流程。既有主模拟的游戏暂停、Actor 筛选、场景活跃检测和全局环境更新不得决定预览是否推进。
第一轮只包含 P 内部的身体／头发或衣物碰撞；重力显式配置，风默认关闭，不带入世界 NPC、地形或天气。

**CBPC**：已找到 [Acro748/CBPCSSE 的公开 C++ 源码](https://github.com/Acro748/CBPCSSE)，旧记录不能再笼统称整个项目闭源。
源码中的 `SimObj::bind/update`、`Thing::update` 与 Actor 的已加载骨架、条件及全局时间／碰撞状态有联系；适配时将节点查找、角色条件、时间步与碰撞集合转为预览上下文输入。
公开源码与测试机 `cbp.dll` 的版本／行为对应关系尚未建立，不能直接宣称复用后等同于该安装版本全部功能。

以下仅为**拟议能力契约**，不是现有 DLL API 名称或已可用符号：

- 创建：输入 P 根节点、装备／碰撞网格、固定版本的配置和预览属性；返回独立句柄及绑定报告。
- 推进：输入该句柄与显式 dt，仅推进其模拟；支持读取状态及有限诊断。
- 重建：按装备代次准备新绑定，在安全边界提交；旧系统解除引用后才能释放旧节点。
- 销毁：停止任务、等待工作完成、注销碰撞／约束／节点引用、释放系统；不得先销毁图再清理后端。

后端实现可扩展物理插件，也可在明确版本和许可条件下复用其求解代码形成独立适配模块；发包前必须选定具体方式并记录。
不以另写一个相似弹簧替代 SMP／CBPC，不冒称原版未修改 DLL 可以自动接入。

#### 更新顺序、坐标与时钟

```text
预览时钟 → HKX／受控基础姿态 → 基础骨架与碰撞输入
        → 按骨骼分工和依赖推进 CBPC／SMP → 物理输出与必要后代更新
        → 包围盒／引擎蒙皮准备 → draw → 面板合成
```

- 受控输入只推动锚点／基础骨架，不直接写被验收的物理输出骨；否则看见摆动可能仅是输入动画。
- 每个物理输出节点只能有明确的最终写入者。两个后端存在依赖时记录执行顺序与状态传递，不能任意互相覆盖。
- 物理输出若采用 world 变换，后续更新必须保留这一语义；不能再用捕获快照、`pose()` 或无条件 local→world 重算覆盖输出。每轮记录物理前、物理后、pass 前三个状态。
- 优先在固定原尺寸摄影棚坐标中模拟，通过相机／输出构图调整大小。当前 0.35 展示缩放需要与模拟单位分离；不能每帧对模拟骨架重复缩放／搬移后仍称参数一致。
- 展示旋转明确选择“相机绕人物旋转”或“物理根运动”。前者不产生惯性；后者要一致变换系统或按规则重置，不能把坐标换算误差当物理响应。
- 使用独立计时来源、固定子步与累积器，记录 dt、子步数和余量。候选 1/60 秒需核对后端原有时间修正约定；同一渲染帧不因多个 pass 重复推进。
- 单独控制动画时钟和物理时钟：冻结基础动作后物理仍可衰减；冻结预览全部更新时双方保持。失焦／长帧后限制补步，不积累数秒时间一次追赶。

每项均需实际求解器身份、节点绑定、模拟状态与画面证据。下表控制名代表测试行为，具体键位由新测试包说明，不沿用 F2／F4 推定能力。

#### 证据、支持范围与停止条件

- 日志至少包含 preview／capture／generation、后端与配置身份、节点／网格绑定、dt／累计模拟时间、任务和分配计数、输入／物理输出／pass 前状态、碰撞事件与来源隔离读数。
- 为 O 与附近 NPC 建立“预览物理关”的暂停基线；用只读骨骼／动画进度观测比较开／关，截图只作补充。装备装配造成的变化另记，不混入无装备操作的隔离窗口。
- 首轮记录已知可用的一个身体／骨架／装备组合；通过后再验证另一套身体及 UBE。配置缺失、骨架不匹配填“阻断／未支持”，不能由一个样本外推全部兼容。
- 出现源角色被推进、共享可变状态、无效引用、非有限数、无法等待任务完成或崩溃，立即停止本轮，保存完整日志与匹配 PDB，后续填未测试。
- 所有数值阈值在发包前写入 manifest，基于单位、配置和暂停基线确定；不在看到结果后调容差。长时间资源／性能预算仍按 §5.3 实测，不填写虚构承诺。

完整通过需包含真实 HKX、CBPC 与 SMP、世界暂停隔离、自动换装和实际回收。仅 V03 或 V05 成立只能证明该样本的独立物理路径。
本次仅更新方案和验收文档，没有修改求解器、动画取数代码或生成新 DLL。

| FR-11 | 跨角色交换与商人交易 | 支持随从之间的物品交换；与商人交易时可切换为随从背包，并由所选随从使用自己的金币和交易能力独立结算。 | 交易能力的具体参与项、买卖资格、随从框架适配，以及交易中切换角色的处理。 |

这里的“角色切换”按用户给出的“切换为随从背包”记录为面板对象切换，不包含附身或操控随从。“随从间交易”首先记录为两名随从之间交换物品，不自行增加随从互相收费的经济规则。

### 9.2 网格展示的边界

**已确认（2026-09-29）：分类 + BG3 风格的单个标准格。**每个物品条目或符合堆叠规则的一组物品占一个统一大小的单元格，不按物品实际尺寸占用多个格子。保留原有负重和物品规则，不引入 Tetris 式拼放、物品旋转或额外空间容量限制。

格子采用较大的展示尺寸，提高物品图标的辨识度。用户的使用预期是分类后每类物品通常较少，因此优先考虑看清物品，而不是追求单屏容纳最多条目；不照搬 BG3 的小格子密度。该预期不是物品数量上限，类别内物品较多时仍需支持正常浏览。

物品图标的获取方式参考 [Grid Inventory](https://github.com/skypia0147-dev/grid-inventory/blob/main/README_EN.md)。其公开说明描述了利用游戏中的物品 3D 模型生成图标的方式；本项目研究该获取思路，不采用它的多格占位规则，也不因此确定直接复用其代码或将它作为依赖。

图标资源的分辨率和构图应匹配较大的单元格，避免仅放大低分辨率图像。具体捕获流程、缓存策略、失败时的显示方式、图标视角与边距，以及标准格的具体尺寸和是否提供用户调节，留待实现与界面原型确定。不同附魔、强化或状态的物品可能共享外形，不能只靠扩大图标来表达这些差异，仍需在详情或状态标识中区分。

保留分类有利于延续使用习惯，实际兼容性仍取决于物品数据、操作入口和目标模组。上述外部项目说明不构成本插件图标获取或任意模组兼容已经实现的证明。

### 9.3 装备面板与角色切换的关系

- 切换角色时，角色名称、库存、装备槽和 P 的外观应属于同一个当前角色；不能出现随从库存搭配玩家装备或旧角色模型的状态。
- P 的展示操作仍与 O 的世界姿态独立。对实际装备的操作需明确作用于哪个角色，并等待游戏确认后的结果再刷新。
- 界面上的“装备槽”与 Skyrim 装备占用并非天然一一对应，多槽护甲、左右手和模组附加装备需要专门映射，不能用 UI 图标位置代替装备规则。

**已认可的设计方向：**主要装备槽围绕 P，额外槽位按需展开，避免把全部内部槽位同时铺在角色周围。由背包界面决定当前角色，渲染模块接收要展示的角色来源；不把整个渲染模块的数据获取固定为玩家单例。M0 仍只验证玩家的单角色展示，不同时实现随从系统。

### 9.4 多方库存与交易规则

界面设计需区分“当前角色／库存拥有者”和“交互对象”。例如与同一商人交谈时，从玩家背包切换为随从背包，不应误把交易对象也换成随从。

**已认可的设计方向：**各界面复用分类、网格、详情与数量选择组件，取放、交换和买卖分别保留自己的规则：

| 场景 | 操作含义 | 需要保留或明确的规则 |
| --- | --- | --- |
| 当前角色自身背包 | 查看、使用或装备物品 | 当前角色是否允许该操作；物品实例、数量和实际装备结果。 |
| 玩家与随从／随从与随从 | 在两个角色库存间移交物品 | 来源、接收者、持有权限及相关随从框架规则。 |
| 当前角色与容器／尸体 | 获取或存入物品 | 目标是否可用、哪些方向允许、所有权及原游戏限制。 |
| 当前角色与商人 | 买入或卖出物品 | 商品来源／去向、金币收支、价格与议价主体、商人买卖限制。 |

**已确认的结算规则（2026-09-29）：随从独立交易。**商人界面选中哪名角色，就使用该角色的库存、金币和交易能力参与交易：

- 买入物品进入当前角色的库存，由该角色支付金币；卖出物品从该角色库存扣除，所得金币归该角色。
- 切换到随从时，不自动使用玩家金币、玩家议价能力或共享队伍钱包。
- 切换角色后，需要按新角色刷新价格、可用金币与交易条件，不能沿用上一个角色的报价或待提交操作。
- 商人仍是当前交互对象，其库存与金币不会因切换买卖角色而被视作新的独立商人副本。

仍需讨论：交易能力中口才、Perk、效果等因素的具体适用方式，商人买卖资格及随从管理框架对库存的限制。无法取得正确主体或条件时，应报告不可用原因，不静默改用玩家规则。两名随从之间的交换暂不因此引入价格或金币结算。

### 9.5 后续推进方向（排期与工作包待细化）

1. 完成可单独验证的单角色渲染及其必要的外观、动作和生命周期能力。
2. 在玩家背包中完成分类网格与环绕装备槽的使用闭环。
3. 将当前角色选择接入库存、装备面板与 P，再实现玩家／随从和随从／随从交换。
4. 统一容器、尸体与商人界面的表现，并落实商人交易中的角色切换和角色独立结算。

单角色渲染优先，以及后续组件复用和角色选择边界已得到用户认可。上述工作拆分仍按依赖关系逐步细化，不构成全部功能同时开工的安排，也不要求现在重写这些模块。

### 9.6 后续验收方向

以下是后续工作包的验收草案，不代替 M0–M3 的现有验收，也不表示尚未确定的规则已获确认。

| 编号 | 场景 | 验收方向 |
| --- | --- | --- |
| B01 | 在不同物品分类间切换 | 各分类以统一标准格显示正确条目，每个条目／合法堆叠占一个格子；数量和物品状态一致，不错误合并不同实例，不引入多格拼放容量。 |
| B02 | 查看及操作环绕装备槽 | 槽位、物品详情和 P 的外观一致；实际装备遵循游戏确认结果。 |
| B03 | 在玩家与随从间切换当前角色 | 名称、库存、装备和角色画面同步切换，旧刷新结果不覆盖新选择。 |
| B04 | 两名随从间交换物品 | 来源、接收者和数量正确；失败时不产生丢失、重复或错误归属。 |
| B05 | 打开普通容器或搜刮尸体 | 使用对应交互界面，获取／存放行为遵守该目标和原游戏的规则。 |
| B06 | 与商人交易期间切换到随从库存 | 商人保持不变；物品和金币直接进出所选角色库存，价格按该角色的交易能力刷新，不自动动用玩家库存或金币。 |
| B07 | 操作期间目标失效或角色切换 | 不将原角色的待执行操作错误提交给新角色，界面给出可理解的状态。 |
| B08 | 查看较大标准格中的物品图标 | 图标获取流程与单格展示配合，图像清晰、构图可辨；类别内物品较多时仍可浏览。外形相同但属性不同的物品可通过详情或状态标识区分。 |

后续优先讨论可选随从范围及交易能力的具体适用规则。网格已明确为较大的统一标准单格，商人结算主体已明确为当前选中角色，不重复作为开放问题。图标获取的具体实现与布局细节可在单角色渲染成立后继续细化。
