# 展示后端路由：交易双方、尸体与基础容器

日期：2026-10-13。依据：[PRD 0.11 §9.7](player-panel-prd.md)。

这是用户确认的后续设计与验收方向，不是已实现能力，不扩大当前 AFP 同 Actor 更新／直绘工作包。
保留 Actor 与场景图两种后端，共用绘制能力，按每个展示实例的对象和需求选择。

## 1. 路由与能力范围

| 来源／展示需求 | 后端 | 必需行为 |
| --- | --- | --- |
| 玩家／当前选中随从 | 克隆 Actor | OAR／展示动作、装备同步、体型／表情／物理按支持范围分别更新 |
| 需要 OAR 的商人 | 克隆 Actor | 自身展示状态的行为图／OAR 求值、最终姿态应用及同 Actor 直绘 |
| 尸体 | 场景图快照 | 保留当前尸体姿态；搜刮可见装备后重新捕获外观；不创建尸体展示 Actor |
| 宝箱等基础容器 | 场景图快照 | 当前模型、材质和所需打开／关闭状态；不创建人物 Actor |

商人动作少不等于无需 OAR 上下文。需要 OAR 时不退回“复制图自动播放 idle”；不需要 OAR 且明确只作静态展示时，可另外声明快照配置。
尸体的“动态更新”指外观更新，不是持续播放身体动作或运行 ragdoll／衣物物理。复制时保留当前形状，更新时保持死亡姿态，不用活体站立模板重新装配它。
容器连续开盖动画是可选控制器工作包；静态状态刷新不要求这项能力，也不能直接推进源容器控制器实现面板动画。

Actor 后端的外观一致性仍需 FR-01、F00–F04、BM00–BM03 证据；创建成功或 OAR 动作相同不能代替身体变形、脸部与装备同步。
场景图能否保留某个模型的当前形变也需样本验证，不能从世界截图正确外推复制正确。

## 2. 共用显示接口与独立实例

展示实例至少明确：来源 handle／类型、交互会话、后端、来源 3D generation、当前请求／提交代次、有效模型、取景、输出、更新策略与资源所有权。
Actor 实例另有图／姿态／FaceGen／体型／物理状态，场景图实例另有捕获姿态和刷新状态；两者不能通过一个全局模式互斥。
准备、更新、刷新、绘制、停止与实际销毁分别由后端提供，界面只决定展示来源及能力要求。

### 交易双方

1. 当前角色侧和商人侧各有自己的 Actor 实例／输出；不共用可变骨架、体型、FaceGen、物理或刷新队列。
2. UI 身份分开：当前角色是库存／金币／交易能力主体，商人是交互对象。切换玩家／随从只替换当前角色侧，商人保持不变。
3. 展示 Actor 的库存只服务装配，不参与买卖结算；实际交易读写原对象，避免把物品卖到克隆库存。
4. OAR 的身份、装备和条件由该展示 Actor 的实际状态决定。明确配置支持范围，不把“克隆商人已生成”当作所有原商人条件完全等价。

### 混合后端

尸体／容器界面若同时展示当前角色与目标，可组合“Actor 人物＋场景图目标”；双方分别刷新，人物动作不能使尸体站起或容器启动人物更新。
当前代码只有玩家来源、单快照／输出，尚不能直接完成这项组合；来源选择、菜单生命周期、来源隔离和资源管理需扩展。

### 绘制与缓存

[共用绘制缝](../src/render/studio/figure_passes.h) 接受 root，但当前每次 batch 清空颜色／深度。
双展示采用各自输出再合成，或明确改为同目标清一次后绘制多对象；顺序调用原 batch 不能算双人物支持。
每个视图恢复自己的渲染状态、光照和取景，互不覆盖。静态图在外观／取景不变时可缓存输出；旋转或输出尺寸改变时重新绘制。
画面输出刷新与模型重新捕获是不同操作，旋转不需要重新从源世界复制模型。

## 3. 尸体搜刮后的刷新

```text
游戏确认物品／装备变化
    → 判定是否影响可见外观
    → 等来源身体／装备装配完成
    → 捕获最新整图并审计
    → 匹配 session／source generation／请求代次后提交
    → 显示新外观并实际回收旧图
```

### 什么需要刷新

- 拿走装备中的护甲、衣服、可见武器或其他实际显示部件：以最终卸装及来源图变化为准。
- 普通库存物品变化、鼠标高亮、未成功的搜刮请求：不直接作为外观已变的证据。
- 尸体来源重建身体网格、体型／外观变化或目标切换：取消旧请求，按新 generation 准备。
- 容器仅库存数量变化：通常不需要重捕获外观；模型／开闭状态实际改变时才刷新。

### 整图捕获与姿态

第一版重新捕获来源最新的有效整图，不按物品名删除某一块几何。
卸装可能涉及身体网格替换、多槽护甲分支、骨架／蒙皮和异步资源；“少了一件物品”不等于“删除一个节点”能还原游戏结果。
刷新应保持尸体当前姿态及既有面板观察方向、缩放和构图，不恢复 T-pose，不移动来源，不需要克隆死亡 Actor 再模拟一次死亡。
如装配临时留下不完整图或错误姿态，先继续等待／阻断并记录，不能把它作为合法刷新结果。

### 合并、提交与失败

- 对连续操作合并请求，保存最新期望外观；完成时必须再次核对来源／会话／generation／请求代次。
- 新模型审计与渲染准备成立后切换；等待时保留最后有效画面并显示更新状态，不能把旧盔甲永久显示当作完成。
- 对超时／缺少有效 3D 给出可理解的未完成状态，回传库存、装备、根／节点和装配阶段；不虚构成功。
- 暂停中来源尸体的装配若不完成，调查定向刷新入口；不得解除全局暂停推进世界，也不通过删除旧几何绕过实际装配。
- 目标被删除／卸载、读档、复活或换为另一交互对象时取消全部旧请求，停止读取旧节点。交互 UI 重新判断资格，不把复活对象继续冒充尸体。

### 旧图回收

切换前明确旧 draw 和异步任务不再使用旧图，解除相关引用，按已验证顺序实际销毁。
当前停放不释放不是生产刷新策略；在 S1／R09 对相应资源成立前，不执行反复搜刮／捕获压力测试。
来源与展示资源隔离仍须审计，源图销毁不能令已承诺独立持有的快照失效。

## 4. 后续游戏内验收 D01–D08

发包前固定源码／DLL／PDB、游戏／依赖版本、菜单和控件、来源样本、后端与支持配置、允许刷新次数、线程／回收证据及数值容差。
这些项需要新的实现和测试包，当前 AFP8 不能执行。

| 项目 | 具体行为 | 通过条件与失败定位 |
| --- | --- | --- |
| D01 后端路由 | 分别打开玩家背包、商人交易、尸体搜刮、宝箱；记录来源 ID／类型、backend、创建对象与功能开关 | 玩家／需 OAR 商人创建正确 Actor；尸体／容器无新增展示 Actor；错误模式阻断，不静默降级 |
| D02 交易双方 | 同时显示玩家与商人，双方用不同动作／装备样本；再将当前角色切为一个支持的随从 | 两方图／输出／状态独立、无互相清屏／串用；商人交互对象不变，实际物品／金币属于原交易主体 |
| D03 混合展示 | 人物 Actor 与尸体快照同屏，分别旋转取景／冻结人物动作；再切换目标为宝箱 | 两种后端并存，无全局模式抢占，静态侧不随人物动作更新，切换不消费旧目标结果 |
| D04 单次尸体卸装 | 一个已稳定死亡样本，截取搜刮前图；取走实际穿着的单槽／多槽护甲各一次，等待来源装配完成 | 对应装备消失、身体与剩余装备正确，倒地姿态／取景保持；记录请求／装备生效／图稳定／提交时点；普通物品搜刮不虚报卸装 |
| D05 连续请求／失败 | 回收前置成立后快速拿走多个可见装备，制造较旧请求晚完成；另测装配延迟／模型不可用 | 最新结果胜出，无旧装备回流；等待／失败状态明确；未解除世界暂停，不删除几何冒充更新 |
| D06 容器状态 | 展示两个不同基础容器，分别捕获已打开／关闭状态，改变库存与取景 | 不创建 Actor，正确显示模型／所需状态；库存变更不无谓重建，取景不修改源容器；连续开盖动画未实现不算静态失败 |
| D07 来源失效 | 在安全边界切交互对象，令旧请求晚到；再按回收前置测试卸载／读档／目标删除或复活 | 旧来源／generation 请求拒绝，旧节点不读，目标资格与 UI 一致；不能把 A 的完成结果提交给 B |
| D08 隔离与回收 | 先记录源节点／姿态／FaceGen／体型及资源基线；执行有限操作，再在释放证明成立后重复打开／刷新／关闭 | 来源不被预览写入，任务／Actor／图／输出资源实际回收并收敛；停放、日志 RELEASE 和无崩溃均不足以通过 |

D04 先做有限单次、同步和引用门槛明确的实验；D05／D07 会话切换压力／D08 重复操作必须等待 S1／R09，不能为了验证刷新积累旧图。
每项报告“通过／失败／阻断／未测试”，保存对应日志、实际输出截图、manifest 和匹配 PDB；异常停止本轮，不在另一个后端上继续并合并为成功。

## 5. 完成边界

路由方向已确认，实际双实例、非玩家来源及搜刮刷新尚未验证。
Actor 后端继续关闭动作、完整体型／脸部、装备、物理和回收各关卡；场景图后端单独证明尸体姿态、容器状态、装配后外观、来源隔离及实际销毁。
具体交易／搜刮布局和性能预算后续确定；当前只更新文档，没有修改代码或生成新 DLL。
