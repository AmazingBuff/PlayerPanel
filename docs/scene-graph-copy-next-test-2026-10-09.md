# 场景图复制：下一轮测试单（2026-10-09）

依据：[PRD 0.6 §6.2–6.3](player-panel-prd.md)。目标是确认骨骼修改是否到达真实 draw，并把静态显示、生命周期、动作与物理分开判定。

## 当前状态与执行前置

当前静态显示初步成立，安全回收阻塞；S2 摆姿未判定，S3 公开接口接入受限但独立模拟未验证。
本次修改仅为文档。当前 F2 路径仍先探针、后 `draw()` 内的 `pose()`；新日志测量点也尚未实现。
**旧 DLL 不满足本测试单准备条件。须先由实施者修正顺序、加入测量并生成有明确身份的新构建，再在游戏中执行。**

准备者检查：

- 固定提交、DLL／PDB SHA-256、CommonLib checkout 和 dirty 状态；不能只用一直未变的 S0 横幅识别多轮探针构建。
- 日志证明调用顺序是：基础摆位 → 探针 → pass 准备 → draw；确认没有第二次快照恢复覆盖修改。
- 确认目标几何真实可见，目标骨骼属于它的 skin root，并有非零顶点权重／有效 palette 映射。名字相同不证明身份相同。
- 见证点须在同一受控子树，且离 pivot 的垂直半径非零；同时记录骨骼朝向变化。若点在转轴上，位置不动不得判无效。
- 单元测试覆盖实际使用的乘法顺序、含非零 pitch／roll 的姿态、缩放与有效见证点；它只证明数学／序列化，不证明 GPU 会消费该数据。
- 初始轮仅改变节点变换，不写未知格式的矩阵缓存；需要进一步干预时先保存原数据、核对布局／空间和地址范围，使用可恢复的有限值。

## 测试 1：静态基线与配对摆姿（优先）

1. 使用测试存档，记录 CBBE 或 UBE、骨架、装备、渲染模组与物理版本。先只做少量捕获，避免当前停放策略累积泄漏。
2. 打开暂停背包，完成一次捕获和静态显示，保存基线截图及目标身体／护甲 draw 身份。F7／F8／F3／F4 按当前构建横幅确认。
3. 保持装备、相机、根方向、光照和捕获编号不变，先探针关，再探针开。优先使用可持续保持的受控姿态，便于两次抓帧对应；不同时改变公式、轴、材质和上传路径。
4. 日志在同一帧的 T0／T1／T2／T3 记录同一个骨骼与几何。检查 T1 的变化是否在 T2 仍存在，再对照画面。
5. 若仍不动，取得探针关／开的配对图形抓帧。选摄影棚真实身体 draw，不选特效、overlay 占位或无权重几何。
6. 核对 VS 与资源绑定、骨骼缓冲的实际范围／偏移、palette／权重及 GPU 内容。仅看到名为 BonesBuffer 的资源不能证明它由所写 CPU 地址上传。
7. 测试停止后退出背包，确认 O 的姿态、位置和正常物理没有异常。没有装备操作时，记录附近 NPC 是否受到额外推进。
8. 在另一种身体配置重复一次；每轮单独保存完整日志和构建身份，不把两个会话的数据拼成同一条因果链。

记录格式：

| 点 | 必填内容 |
| --- | --- |
| T0 | 提交／DLL、capture、渲染帧号、几何／pass／skin 根／骨骼身份、基准 world、根变换 |
| T1 | 写入前后 world、增量、见证点／朝向变化、候选 CPU 指针及写入前内容 |
| T2 | 实际 pass.geometry、相同 world／CPU 内容、skin.frameID、numMatrices、allocatedSize 与使用的单位 |
| T3 | draw 后 world／CPU 内容、GPU 缓冲身份／绑定范围／偏移／内容、配对画面 |

比较矩阵时，将所有候选统一为相同布局、分量数量和坐标空间；分别说明旋转、平移和缩放。
不得直接把 NiTransform 的原始内存当成 3×4，也不得把 4 分量误差与 12 分量误差直接排序。
不得用刚写入后的值给原始缓存“分类”；CPU 写入成功不是 GPU 数据链成立的充分条件。

## 测试 2：生命周期（S1 单独的准备与执行）

当前 F4／读档将副本停放，不代表释放。不要仅凭无崩溃或记账数量最多 12 判断回收通过。

1. 实施者先定位已发生的三个析构崩溃路径，明确实际所有权、分配器、注册关系、在途任务和线程／时点要求。
2. 根因明确并有修订构建后，从单个副本的一次实际释放开始；记录析构开始／结束、引用关系和是否仍被引擎／模组使用。
3. 记录全部分配，包括活跃、停放以及已经丢掉记账指针但仍分配的图。容器长度不能作为总量。
4. 再验证有限次数重新捕获／换装、读档、主菜单和直接退出；对照内存／显存基线、缓存预热平台和趋势。
5. 任一路径崩溃或每次操作持续增加未回收资源，S1 保持阻塞。栈中出现骨骼树只能作为线索，不能直接认定全局注册根因。

## 测试 3：动作与指定物理（本轮摆姿通过后另行实施）

- HKX：真实播放至少一个稳定待机和一个可切换展示动作；暂停中只推进 P；根运动、装备附着和切换无源角色副作用。
- CBPC：记录支持版本、配置匹配、受控节点、独立状态与更新时间；不能用程序化摆动或只有世界 Actor 生效替代。
- SMP：记录对应 XML、骨架／头发／护甲映射、系统归属、注册／定向推进／注销。只恢复整个 FSMP 世界更新不构成通过。
- 两套物理分别验收，明确分工；正常装备操作造成的源图刷新与额外模拟推进分开观察。
- 若公开接口不足，记录限制与候选扩展，不直接宣布整个物理模组不可实现，也不自行降低用户要求。

| 编号 | 要回答的问题 | 通过／有效性条件 |
| --- | --- | --- |
| R01 | 当前 DLL 是否确实修正了顺序？ | manifest 与日志匹配，T0→T1→T2→T3 可追踪 |

| R06 | 画面是否跟随？ | 配对画面与 GPU 证据一致；同一 capture、相同其他条件 |
| R07 | O 与 NPC 是否保持正常隔离？ | 无意外姿态／位置变化，无因 P 而额外推进物理 |
| R08 | S1 是否真的释放并回收？ | 单独修订构建有实际析构、完整分配统计与内存／显存趋势证据 |
| R09 | HKX、CBPC、SMP 是否分别实现独立驱动？ | 各自记录结果；没有实现填未测试，不用摆姿通过替代 |

R01–R03 不成立时，后续 GPU／路线结论不计为有效否定。R04 被覆盖时先修执行链。
R04 成立但 R05 失败时定位上传路径；R05 成立而 R06 失败时再核对权重、矩阵空间与实际 draw。
只有端到端摆姿成立，才继续 HKX／物理；是否改换架构需根据有效证据重新评估。
