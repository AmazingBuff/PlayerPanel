# 引擎渲染路径验证与 CS 适配回退

- 日期：2026-10-16
- 决策：**先验证能否复用引擎已有的渲染流程；验证不满足要求，就退回当前 `cs-view1` 方案。**
- 当前状态：验证计划已确定，候选入口与游戏内对照诊断尚未实施。本次提交保留现有渲染实现，不提前切换后端。
- 当前方案：[CS 1.9.1 独立材质视图](community-shaders.md)。已有本地构建和 GPU 验证，游戏内正确性仍待确认，不能称为已验证稳定的后端。

## 1. 要确认的问题

在安装并启用 CS 的游戏中，PlayerPanel 是否能通过正常引擎调用，完成独立人物视图所需的材质处理，从而减少或移除对 CS 私有函数与对象布局的依赖？

成功范围遵循 [PRD §2.1／§2.2](player-panel-prd.md)：原材质着色、必要的皮肤散射与材质合成、正确透明处理，以及符合最终合成目标的色彩输出。摄影棚相机、灯光、背景和深度独立；不要求重复执行世界景深、世界时域效果或全部世界后处理，也不要求不同照明／视角下像素相等。

不能仅根据“存在 CS”“人物能显示”“进入某个 hook”判断成功。需要同时证明：正常调用确实触发必要阶段，这些阶段处理的是人物视图的数据，并且退出后没有污染世界渲染。

## 2. 已有证据与未知项

| 项目 | 当前证据与边界 |
| --- | --- |
| 现有绘制入口 | [figure_passes.cpp](../src/render/studio/figure_passes.cpp) 已经通过 `BSBatchRenderer::SetupAndDrawPass` 提交。它不是另写一套人物材质着色器。 |
| 逐材质接入 | CS 对 `BeginTechnique`、`SetupGeometry`、dirty-state 更新等位置接入材质处理；经过这些路径不等于完成整个视图的散射与合成。 |
| 场景阶段接入 | CS 的世界包装、延迟阶段开始／结束包含调用点补丁。插件新增一个对目标函数的直接调用，不会自动经过引擎原来的那个调用点。 |
| 阶段的前置条件 | CS 的 `StartDeferred`／`EndDeferred` 检查世界阶段状态，并使用当前相机、累加器及引擎目标表；不能仅凭函数被调用就判断其工作有效。 |
| 场景入口候选 | 应追踪菜单场景、累加器结束分派和批次提交的调用链。CommonLib 中存在相关声明，但还没有证明某个入口可以独立完成本任务。 |
| `Main::RenderWorld` | 它的包装参数没有人物 root、相机及输出目标三项独立视图契约；不能直接假定重跑它就只会渲染面板人物。 |
| 当前调度位置 | [render_hook.cpp](../src/render/render_hook.cpp) 在原 UI 函数返回后调用面板回调。候选调度需另行检查阶段完整性与 UI 覆盖顺序，不能把现有日志中的“pre-UI”名称当作调用顺序证明。 |

源码依据：[CS 1.9.1 Hooks.cpp](https://github.com/community-shaders/skyrim-community-shaders/blob/v1.9.1/src/Hooks.cpp)、[Deferred.h 的安装位置](https://github.com/community-shaders/skyrim-community-shaders/blob/v1.9.1/src/Deferred.h)、[Deferred.cpp 的阶段处理](https://github.com/community-shaders/skyrim-community-shaders/blob/v1.9.1/src/Deferred.cpp)。源码／PDB 可以支持静态定位；重入、视图隔离及真实 GPU 输入仍需游戏内证据。

## 3. 当前回退基线

本轮回退目标是**现有 `cs-view1` 的独立材质方案**，不是移除 SSS 后退到普通 forward 绘制。它包括版本保护、独立材质与深度缓冲、原生 CS 散射／合成、摄影棚灯光与反射、透明阶段和状态恢复。

同时区分已有的运行时保护：当前方案在 CS 未启用、二进制不匹配或资源／着色器不可用时，可以进入 forward 回退。该保护不表示 forward 已满足完整 CS 材质验收，也不能拿这种降级画面证明引擎候选通过。

包含本文的提交保存当前实现。现有测试包 `CharacterPanel-scopy-cs-view1-1.2.1.zip` 的身份和 SHA-256 记录在 [当前方案文档](community-shaders.md)；它仍对应制作时的源码基线和 dirty 标记。后续提交不追改已有包的身份，也不把当前包冒充成引擎路径诊断版。

未来验证版应显式区分候选与当前实现。引擎路线全部通过前，保留当前实现的代码及可恢复构建，不以候选替换默认行为。验证版的选择开关、诊断标记和日志均是后续工作，本次没有新增这些运行入口。

## 4. 分阶段验证

### E00：冻结环境与当前结果

记录 Skyrim / SKSE、CS DLL 身份及启用的功能、Linear Lighting、SSS 算法和相关渲染插件。使用相同角色、装备、姿态、相机与摄影棚设置做对照；先确保选择的裸露皮肤具有有效 SSS mask，并完成着色器预热。

保留当前包、manifest、完整日志和代表画面。若当前方案本身出现问题，先记录问题，不能把它当作正确的视觉真值；正常世界人物可作为 CS 阶段与材质行为的参考。

### E01：静态追踪候选

从菜单场景、累加器结束／分派、批次提交三类入口建立调用图，逐个核对函数签名、正常调用者、所需对象与渲染阶段。候选需要能明确说明人物 root、相机、目标和 pass 生命周期从何处取得。

逐项标注 CS hook 属于函数入口、虚表还是特定调用点；确认候选是否真的经过对应补丁。记录涉及的引擎全局状态和恢复方式。没有闭合前置条件的入口，不直接在游戏中盲目调用；不把整个世界渲染函数当成可重入的独立视图接口。

### E02：增加只观察的诊断

为人物视图分配关联标记，记录帧号、线程、root、相机、累加器、阶段、调用栈和 GPU 资源身份。通过 PDB 断点或转发原函数的观察 hook，追踪逐材质、阶段开始／结束、SSS 与合成。

观察 CS 内部入口用于确认行为，不要求正式引擎后端调用这些内部函数。CPU 阶段和 GPU 工作可能不严格嵌套在同一个日志窗口内，必须用视图与资源关联，不能仅用总调用次数判断。

### E03：三组对照

| 组别 | 路径 | 目的 |
| --- | --- | --- |
| A | 游戏正常渲染世界人物 | 记录已启用 CS 功能的正常阶段、着色器与数据要求；不把世界光照当作摄影棚像素真值。 |
| B | 当前逐 pass 引擎绘制，禁用 PlayerPanel 手动 CS 适配 | 查清现有调用自动覆盖的范围。 |
| C | 候选的更高层引擎路径，同样禁用手动 CS 适配 | 验证候选能否自动完成必要阶段。 |

B／C 关闭的是 **PlayerPanel 的手动适配**，游戏 CS 保持启用。不得写入 CS 的 `inWorld`／`deferredPass`，替换其私有缓冲包装器，或主动调用 CS 的散射／合成来补齐结果，否则不能得出“引擎路线自动生效”的结论。

候选可以通过已核对的引擎／D3D 接口建立摄影棚资源与上下文；所有修改需有对应恢复。独立相机、装备和材质必须与测试记录一致，不以共用世界相机或省略透明层换取表面通过。

### E04：GPU 帧证据

捕获同一测试条件下的 D3D11 帧，核对实际 draw／dispatch 和资源关系。可使用 [RenderDoc](https://github.com/baldurk/renderdoc) 或等价 GPU 调试手段。每项记录资源身份、尺寸、格式和对应视图，而不是只截图一张最终画面。

| 必须核对的证据 | 通过含义 |
| --- | --- |
| 人物 draw 与着色器 | 对应人物 root 的几何使用预期的 CS 材质变体。 |
| 材质缓冲与深度 | 人物确实写入所需输出；深度、法线、反照率及 mask 属于这个视图。 |
| SSS | 对有散射需求的皮肤，存在真实有效的计算派发，读取其材质与深度；仅进入 `DrawSSS` 后提前返回不算通过。 |
| 材质合成 | 合成读取本视图的数据及正确相机常量，输出供面板使用；不是处理了世界图像后复制一块颜色。 |
| 透明与色彩 | 眉毛、眼影、头发及装备透明正确；输出编码匹配合成目标，不重复色调映射。 |

SSS 模式及 Linear Lighting 开关作为交叉验证：画面变化需能对应到真实着色器／输入变化，不能仅凭“看起来更柔和”下结论。安装的 HDR／其他效果也要按实际接入阶段记录。

### E05：世界隔离与行为检查

对比人物视图前后的世界颜色、深度、材质／历史资源和关键上下文。世界正常渲染已经发生的写入应单独标识，不能和预览引入的额外写入混算；最终 framebuffer 上面板矩形的正常合成也不等于世界场景缓冲被污染。

确认世界历史没有因预览额外推进，相机、累加器、目标绑定及 CPU/GPU 缓存能恢复。检查打开／关闭背包、转动预览、快速换武器与头部装备、读档后再次打开，以及室内／室外、天气和动态分辨率变化。窗口外世界、下一帧、UI 遮挡顺序及既有 UBE 妆容结果均须正常。

既有独立动作链继续满足站立 idle、有限切换及最新装备打断约束，不通过改动世界角色姿态、生成新的世界 Actor 或修改来源外观来完成此渲染验证。

### E06：判定、切换或回退

| 结果 | 决策 |
| --- | --- |
| 必要阶段、输入归属、独立相机与世界恢复全部通过 | 引擎路线可进入替换实现；只移除已证明被覆盖的私有适配，并重新完成两种人物来源的构建与游戏回归。 |
| 仅自动接入逐材质 hook，缺少必要 SSS／合成 | 候选未通过；按 E01 已定位的其他入口继续验证。不能关闭必要效果后宣称成功。 |
| 阶段执行但混用世界输入、重复更新历史或无法恢复 | 停止该候选，恢复当前方案。修复隔离必须有明确证据，不能靠反复试改私有偏移延续实验。 |
| 本轮候选无法满足要求，或无法取得关键游戏／GPU 证据 | **退回并保留当前 `cs-view1` 方案**，将引擎路线记录为未通过／未能确认，不继续扩大实验替换范围。 |

“未能确认”不等于所有引擎路线都不可能。部分功能可复用也不构成本轮整体通过；若后续要采用混合方案，单独说明覆盖范围、剩余私有依赖及验证证据。

回退时使用本提交保存的渲染实现恢复构建，恢复验证前的选择与调度，不删除现有版本保护、资源隔离和透明材质处理。对恢复结果核对构建身份、日志和代表画面，再做打开／关闭面板与世界恢复检查。

## 5. 必须保留的验证记录

每个候选至少保存以下内容，供后续选择后端及回退复核：

- 引擎入口、签名、正常调用者、调用图、CS 补丁类型及实际经过的补丁位置。
- 游戏／CS／功能设置、构建选项、源码提交、DLL/PDB 身份及包 manifest。
- A／B／C 阶段日志和对应帧捕获，人物视图的资源关联与相机常量。
- 必要效果、世界隔离、状态恢复、UI 与动作／装备检查结果。
- 判定：通过、未通过或未能确认；失败环节及恢复使用的基线。

目前可确认的仍是当前方案的两种 Release 构建、31 项已有检查、5 项资源／状态／编码／profile 检查和 16 项官方 HLSL 案例。它们不执行游戏内候选引擎流程，不能代替 E02–E06 的证据。
